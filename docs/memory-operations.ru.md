# Эксплуатация на iMac с 8 ГБ памяти

[Русский](memory-operations.ru.md) | [English](memory-operations.md)

## Что было причиной перегрузки

Standalone scheduled task Codex создавал новую Codex-задачу каждые пять минут.
Старая аренда защищала только уже заявленный event ID. Если новый ответ X
появлялся во время активной публикации, следующий scheduled run получал новый
claim и поднимал второго Sol High Browser owner. Одновременно росли Electron
renderer, app-server, `node_repl`, MCP helper и списки задач в интерфейсе.

Это подтверждено журналами реального запуска 26 июля 2026 года:

- run 07:24 еще работал до 07:31;
- run 07:29 уже заявил другой event;
- run 07:34 стартовал до завершения второго владельца.

## Новый контракт

1. В dispatcher существует одна глобальная аренда владельца.
2. Новый event ждет завершения активного владельца, даже если его ID раньше не
   арендовался.
3. Idle run владеет нулем Browser-вкладок.
4. Short использует одну X-вкладку.
5. ChatGPT открывается только после доказанного Pro route.
6. Pro использует максимум одну X, одну ChatGPT и одну generation.
7. Все task-owned вкладки закрываются при terminal исходе.
8. Luna Low выполняет только read-only gate. Sol High не запускается для
   пустой, занятой или отложенной очереди.
9. Только готовая очередь будит одну закрепленную сессию Sol High, которая
   выполняет атомарный claim до загрузки skills.
10. Resource guard проверяет состояние до Browser. `resource_deferred`
   сохраняет очередь без изменений.
11. Активный голосовой разговор всегда откладывает тяжелую Browser-работу.
   Последнее обнаружение микрофона удерживает паузу еще пять минут.
12. Отдельный безмодельный LaunchAgent архивирует завершенные служебные задачи
    через локальный Codex app-server. Он не создаёт новую задачу и не расходует
    токены.
13. Тот же LaunchAgent освобождает осиротевший claim только когда связанная с
    ним задача неактивна и не обновлялась минимум пять минут.
14. После завершенного scheduled run janitor сопоставляет точное время создания
    задачи с bundle ее `node_repl` и MCP helper. Через 120 секунд он отправляет
    `SIGTERM` только helper-процессам этой уже неактивной задачи. Текущий
    владелец, защищенные задачи и процессы без точного временного соответствия
    никогда не затрагиваются.

## Автоматические режимы

`resource_mode: auto` выбирает режим перед каждым непустым claim. Выбор влияет
только на допуск Browser-работы. Модель Sol High, фактчекинг и правила
публикации не упрощаются.

| Режим | Когда | RSS Codex | Renderer | Свободная память | Swap |
| --- | --- | ---: | ---: | ---: | ---: |
| Экономный | голос или давление памяти | 2200 MiB | 5 | минимум 20% | до 896 MiB |
| Сбалансированный | пользователь работает | 2350 MiB | 6 | минимум 14% | до 1024 MiB |
| Максимальная производительность | простой 15 минут, питание от сети, свободно минимум 35% | 2500 MiB | 7 | минимум 12% | до 1152 MiB |

Жесткий предохранитель действует во всех режимах: RSS 2700 MiB, 8 renderer,
минимум 10% свободной памяти и не более 1280 MiB swap. Лимиты 10 `node_repl`
и 20 MCP helper остаются строгими, когда их суммарный RSS велик или текущей
свободной памяти мало. Большое число лёгких helper считается диагностикой, а
не причиной навсегда остановить готовую очередь. При срабатывании
предохранителя новый Browser owner не стартует, а event остаётся в durable
очереди.

macOS может долго сохранять уже выделенный swap после того, как нагрузка
закончилась. Поэтому один только старый абсолютный swap не блокирует очередь
навсегда. Если свободно не менее
`memory_guard_swap_recovery_free_percent` памяти и RSS Codex не выше
`memory_guard_swap_recovery_codex_rss_mb`, swap считается историческим:
память, renderer и helper-лимиты продолжают действовать. При текущем давлении
памяти swap снова становится блокирующим сигналом.

Голосовой приоритет не останавливает минутный watcher, watchdog, SQLite или
очередь. Он запрещает только тяжелый Browser owner. После последнего
обнаруженного входа микрофона guard сохраняет паузу на
`voice_priority_hold_seconds`, по умолчанию 300 секунд. Поэтому короткая тишина
между голосовыми репликами не считается завершением разговора.

Счетчики helper являются ранним сигналом, а не самостоятельным доказательством
утечки. При свободной памяти не ниже
`memory_guard_helper_recovery_free_percent`, RSS Codex не выше
`memory_guard_helper_recovery_codex_rss_mb`, а измеренном суммарном RSS helper
не выше `memory_guard_helper_recovery_total_rss_mb`, превышение числа
`node_repl` или MCP не блокирует очередь само по себе. За пределами этого
контура лимиты снова становятся строгими. Режим максимальной
производительности дополнительно требует
`resource_mode_performance_min_free_percent`, поэтому одного простоя
пользователя недостаточно для самого агрессивного профиля. Renderer-лимит не
смягчается. При недоступном отдельном системном замере guard записывает ошибку
в `var/resource-health.json` и не теряет event.

## Измеренный расход пробуждения

Три реальных пустых или отложенных Luna Low run 26 июля 2026 года использовали
в среднем 49 064 обработанных токена. При интервале пять минут это примерно
588 768 обработанных токенов в час. Два прежних guard-only Sol High run
использовали в среднем около 59 993 токенов, примерно 719 916 в час.

По объему контекста экономия составляет около 18%. Денежная экономия выше,
потому что Luna дешевле Sol, но эти значения не являются счетом провайдера.
Минутный watcher, watchdog и janitor остаются полностью безмодельными.

## Почему архивирование обязательно

Официальная документация Codex предупреждает, что standalone scheduled task
начинает новый chat при каждом запуске. Самоархивация активной задачи может
оставить ее в состоянии `active`. Модельная housekeeping automation тоже
оказалась непригодна: она сама создавала новые задачи. Поэтому
`scripts/session_janitor.py` запускается обычным LaunchAgent каждую минуту.
Он архивирует завершенные задачи старше одной минуты с точным Automation ID,
не затрагивает активного владельца и защищенную закрепленную задачу, сохраняет
историю для восстановления. Активный owner больше не останавливает housekeeping:
janitor всё равно архивирует другие завершенные задачи и убирает их helper.

Статус последнего прохода перезаписывается в
`var/session-janitor-health.json`, поэтому журнал не растёт бесконечно.
Связь claim с задачей определяется по времени создания до claim и последнему
обновлению. Более поздние пустые scheduled runs не могут замаскировать
осиротевшего владельца.

Каждый scheduled run может оставлять дочерний bundle из `node_repl`, Node MCP
и Python MCP даже после завершения самой задачи. Janitor удаляет только bundle,
чье время старта совпало с конкретной завершенной X-задачей с допуском две
секунды. Используется только мягкий `SIGTERM`; выживший процесс записывается в
health state и не добивается принудительно. Это сохраняет fail-closed поведение
при неоднозначном владельце и предотвращает накопление helper каждые пять
минут.

## Проверка после обновления

1. Выполнить полный unit test suite.
2. Запустить пустой scheduled run и подтвердить: Browser не открывался, задача
   нормально завершилась.
3. Подтвердить, что безмодельный janitor архивировал ее после минимального
   возраста, не создав новую задачу.
4. Дождаться реального X event и подтвердить один global claim.
5. Во время активного claim добавить или дождаться второго event.
6. Подтвердить, что второй run вернул `owner_busy`, не открыл Browser и не
   заменил `work_in_progress`.
7. После завершения первого владельца подтвердить claim второго event.
8. Сравнить `var/resource-health.json`, RSS и число renderer до и после.
9. Прервать тестовый owner и подтвердить recovery только после устаревания
   связанной задачи, без ложного освобождения живого `notLoaded` run.
10. После завершения canary подтвердить уменьшение числа его helper-процессов,
    отсутствие PID текущего владельца среди целей и запись результата в
    `var/session-janitor-health.json`.
